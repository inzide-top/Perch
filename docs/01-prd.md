# Agent Seek Employment — PRD（MVP v1）

## 1. 文档目的

`Agent Seek Employment` 是一个本地优先的求职辅助 Web 应用。它围绕“简历版本 → 岗位机会 → JD 匹配 → 模拟面试 → 能力画像”形成闭环：不是只输出一次分析，而是利用用户的历史证据，持续决定下一步该准备什么、该问什么。

本 PRD 固定一个月内可交付的 MVP 范围。产品目标是：

- 帮助用户更有依据地评估一个岗位与某个简历版本的匹配关系；
- 在多次基础面、项目面之间积累能力证据，生成更有针对性的追问；
- 让开发者能够展示 AI workflow、结构化输出、状态记忆、检索、工具调用与 Agent 可观测性；
- 首先支持单用户本地使用，后续再加入登录、云同步和部署。

## 2. 用户与核心场景

### 2.1 目标用户

- 正在求职、拥有一到两份主要简历的人；
- 会同时查看或投递多个岗位，需要比较岗位和准备面试；
- 希望保留真实的简历修改历史和面试复盘，而不是每次重新开始。

### 2.2 核心用户旅程

```text
创建一份简历主线
  → 保存简历版本 V1
  → 新建岗位，粘贴 JD，选择 V1
  → Agent 生成 JD 匹配报告
  → 做基础面 / 项目面模拟
  → Agent 更新能力项与下一轮面试计划
  → 用户修改简历，保存 V2
  → 系统提示旧岗位分析基于 V1；用户可保留历史或基于 V2 重新分析
  → 多份 JD 的信号汇总到“求职策略”中，而非产生大量重复简历建议
```

## 3. 成功标准

### 3.1 产品验收

1. 用户可建立一条简历版本链，并能查看任一历史版本。
2. 一份岗位分析固定记录所用的简历版本；后续版本出现时，用户可主动重新分析，不会悄悄覆盖当前结果。
3. 用户可从 JD 分析进入模拟基础面或项目面，完成至少三轮问答。
4. 项目面的问题会同时参考 JD、关联简历项目和历史能力项；不会机械重复已验证的基础题。
5. 系统能把多份 JD 中的重复需求合并为有限的“求职策略建议”。
6. 开发者可在调试页查看一次 Agent Run 的主要步骤、输入摘要、工具调用与结果。

### 3.2 作品集展示标准

可用真实简历和 3–5 份真实 JD 完成一次演示，讲清楚：

- 为什么一个岗位必须绑定简历版本；
- Prompt 如何拆分为抽取、匹配、出题、评分和聚合；
- 长期记忆如何通过能力项与会话摘要实现；
- 哪些地方使用 RAG，哪些地方不该使用向量检索；
- Agent 工具如何校验、记录、失败降级和受权限约束。

## 4. MVP 范围

### 4.1 必须做

1. **单用户本地模式**：无登录；数据可存本地数据库或本地开发 Supabase 项目。
2. **简历管理**：新建多份简历；一份简历内按保存动作产生单线版本；编辑、预览、切换版本。
3. **岗位机会管理**：新增岗位、粘贴 JD、选择简历版本、设置状态和优先级。
4. **JD 匹配分析**：异步状态展示；结构化输出六个通用维度、匹配证据、优势、缺口、岗位专属风险和面试准备建议。
5. **机会详情**：岗位概览、信息管理、JD 分析、模拟面试。
6. **模拟面试**：基础面和项目面；逐题问答；单题反馈；本轮总结；能力项更新建议。
7. **跨 JD 求职策略**：按能力标签聚合多个 JD，展示 Top 5–8 条可执行建议及其来源岗位。
8. **Agent 调试页**：仅开发环境显示 Agent Run、步骤与错误。

### 4.2 明确不做（MVP 后）

- 登录、多人协作、云端同步、支付；
- 图片 OCR、复杂 PDF/Word 解析、自动抓取招聘网站；
- 语音面试、录音转写与实时语音；
- 多个可命名的岗位内聊天会话、首页全局操作型对话；
- 自动投递、自动修改外部招聘平台；
- 真正多 Agent 编排、队列 Worker、批量分析数百个 JD；
- 第三方 MCP、GitHub / Google Drive / Calendar 授权接入。

## 6. 功能需求与规则

### 6.1 简历主线与版本

- 一份“简历”代表一个独立求职方向；不同方向应新建不同简历，而非从旧简历分叉。
- 同一简历内只有一条线性版本链。用户每次显式点击“保存为新版本”，系统创建 `V(n+1)`；不根据内容自动命名版本意图。
- 输入过程可保留草稿，但只有显式保存才生成正式版本，避免每个输入字符形成版本。
- 每个版本保存完整内容快照、父版本、创建时间、可选修改说明和结构化 diff 摘要。
- 简历摘要与标签：首次保存自动生成；后续编辑只标记“摘要可能过期”，由用户点击重新生成。MVP 不做字段级智能增量刷新。

### 6.2 岗位与历史版本

- 新建岗位时必须选择一个**具体简历版本**，而不只选择简历主线。
- `JobAnalysis` 保存当前 JD 与指定简历版本的有效分析结果。用户主动重新分析时，当前结果被更新；每一次模型尝试保留在 `AgentRun` 中供开发者回看。
- 若关联简历已有更新版本，进入机会详情时显示提示：

  > 当前分析基于简历 V1；检测到 V2、V3。你可继续使用历史版本，或基于最新版本重新分析。

- 后续旧面试记录永远可查看；新分析只携带可迁移的能力画像摘要，不直接塞入全部旧聊天记录。

### 6.3 JD 分析

对每份 JD 依次完成：

1. 抽取结构化岗位需求；
2. 归一化为能力标签；
3. 从关联简历版本中查找证据；
4. 输出匹配结论与面试准备项；
5. 将可聚合信号写入求职策略数据。

创建前会对公司、岗位、城市和 JD 原文生成规范化精确指纹。仅忽略空格、换行、标点、全半角和英文大小写；若检测到同一用户已有完全相同 JD，不新增第二条机会，而是让用户查看已有结果或对已有机会强制重新分析。

需求项必须保留原文片段、判断理由和置信度。不得仅根据“精通 / 熟悉 / 了解”给出伪精确评分。

岗位要求强度综合考虑：出现位置（职责/要求/加分项）、与岗位核心职责的相关性、重复强调程度、措辞强度及 JD 清晰度。候选人证据强度则独立根据简历和面试证据判断。

### 6.4 模拟面试与能力画像

- 基础面：验证技术概念和基础知识。
- 项目面：验证用户能否结合自身项目、JD 场景和真实结果进行表达与权衡。
- 两类会话共享能力项，但评分标准不同。
- 每次回答可生成：分数、表现证据、问题、改进建议、关联能力项。
- 一轮会话结束后生成固定总结。会话结束后不得悄悄重写历史分数；用户再次评分应产生新的评分版本或明确的重新评分记录。
- Agent 自动保存原始评分证据；对“长期能力画像”的新增/调整以建议卡展示，用户可以接受、编辑或忽略。

### 6.5 求职策略中心

岗位详情中的建议只回答“这个岗位的风险/准备方式”。跨 JD 的简历策略在外层统一维护。

策略卡按能力标签聚合，至少包含：

- 建议主题；
- 覆盖岗位数、来源岗位、岗位优先级；
- 市场信号强度；
- 简历现有证据；
- 建议动作；
- 分类：`补充真实证据`、`优化已有表达`、`学习/项目建设`、`仅定制简历考虑`、`不建议行动`。

默认只展示 Top 5–8 条；可按简历、岗位状态、时间范围筛选。系统不能因为少数 JD 提及某技术就建议用户将其写入通用简历。

## 7. Agent 工作流

第一版采用一个协调器与多个明确阶段，不实现多个独立子 Agent：

```text
输入/用户动作
  → 读取结构化上下文
  → 执行对应工作流
  → 校验结构化输出
  → 写入状态与审计轨迹
  → 返回用户可理解的结果
```

工作流：

| 工作流   | 阶段                                                            |
| -------- | --------------------------------------------------------------- |
| JD 分析  | 需求抽取 → 简历证据匹配 → 分析报告 → 写入聚合信号               |
| 基础面   | 读取 JD 与能力画像 → 计划问题 → 回答评分 → 更新建议             |
| 项目面   | 读取 JD、简历项目、基础面证据 → 计划题目/追问 → 评分 → 更新建议 |
| 求职策略 | 读取规范化需求信号 → 去重/排序 → 生成有限行动建议               |

## 8. 开放项（不阻塞骨架）

- 简历导入先支持粘贴文本还是仅支持手工表单；
- 单题评分是否默认自动生成，或由用户点击生成；
- 模拟面试一轮默认题数（建议 5 题）；
- 岗位状态枚举的最终文案。
