# AI 分析与 JD 匹配框架

## 当前实现（2026-08）

当前版本已经不再是纯 mock：服务端会把 JD、指定简历版本和模型连接配置组成受控输入，调用模型后以 Zod 校验完整 JSON 结果。当前为降低首次落地复杂度，采用**单次结构化匹配 Prompt**，直接输出六个固定维度、要求匹配、优势、风险、简历建议和面试关注点。

工作流如下：

```text
创建 / 重新分析
  → 创建 JobAnalysis 与 AgentRun
  → 模型请求
  → JSON 解析 + Zod 校验
  → 校验失败时带字段错误发起一次修复请求
  → 成功写入当前分析结果；失败保留 AgentRun 错误与原始输出
```

本文件余下内容是下一次 Prompt 拆分时的目标设计，不代表这些中间对象已经全部入库。

## 目标

当 JD 分析稳定、且需要复用独立的简历/JD 结构化结果时，再将当前单次匹配 Prompt 拆成三段：

1. 简历结构化分析：`ResumeContent -> ResumeAnalysis`
2. JD 结构化分析：`JobOpportunity -> JobRequirementAnalysis`
3. 简历与 JD 匹配：`ResumeAnalysis + JobRequirementAnalysis -> JobAnalysis`

这样做的好处是：

- Prompt 更短，约束更清晰
- 每一步都可以单独调试和复用
- 结构化数据能服务后续模拟面试、简历优化和跨 JD 策略
- 出错时更容易定位是简历抽取问题、JD 抽取问题，还是匹配评分问题

## Step 1：简历结构化分析

输入：

- `Resume`
- `ResumeVersion`
- `ResumeContent`

输出：

- `ResumeAnalysis`

重点提取：

- 候选人定位：前端开发、AI 应用前端、工程化方向等
- 意向城市：城市列表、灵活度、原因
- 技能信号：技能名、类别、熟练度、证据
- 项目信号：业务领域、技术亮点、成果证据
- 优势：用于展示和面试信心建设
- 风险：用于后续简历优化和模拟面试追问

## Step 2：JD 结构化分析

输入：

- `JobOpportunity`

输出：

- `JobRequirementAnalysis`

重点提取：

- 岗位业务背景：这份工作服务什么业务、用户、场景和协作链路
- 核心要求：JD 明确要求候选人必须具备的能力、经验、资质或条件
- 相关经历要求：JD 暗含或明示需要怎样的过往项目、工作、业务或实践经历
- 能力层级要求：JD 中的“精通 / 熟练 / 独立负责 / 主导 / 了解 / 优先”等强度表达
- 加分项：JD 中“优先 / 加分 / 有更好”的内容，不应和硬性要求混淆
- 求职条件：城市、学历、语言、证书、身份、到岗状态、出差/倒班等客观条件
- 每条要求的重要性：`must_have` 或 `nice_to_have`
- 要求等级：`expert`、`proficient`、`familiar`、`basic`、`preferred`

注意：这里不能把某个具体行业或具体岗位能力写成固定字段。比如 AI Native、RAG、Agent、Vue、React、财务证书、机械制图、用户研究等，都只能作为某次 JD 里的 requirement signal 或 gap，而不能成为所有岗位都固定展示的顶层评分维度。

## Step 3：简历与 JD 匹配分析

输入：

- `ResumeAnalysis`
- `JobRequirementAnalysis`

输出：

- `JobAnalysis`

第一版通用评分权重：

| 维度         | 权重 | 说明                                                                |
| ------------ | ---: | ------------------------------------------------------------------- |
| 核心要求匹配 |   30 | JD 明确要求的能力、经验、资质、工具或硬性条件，候选人是否满足       |
| 相关经历匹配 |   25 | 简历中的项目、工作、实践经历是否能支撑该岗位，不限定互联网行业      |
| 能力层级匹配 |   15 | JD 要求“精通/主导/独立负责/熟练/了解”时，候选人证据是否达到对应深度 |
| 业务场景匹配 |   10 | 是否有相似行业、业务、用户场景，或是否存在清晰可迁移性              |
| 加分项匹配   |   10 | JD 中“优先/加分/有更好”的内容，候选人是否具备                       |
| 求职条件匹配 |   10 | 城市、学历、语言、证书、身份、到岗状态等客观条件                    |

这个评分框架是产品层固定 Rubric，不是岗位模板。后端 Prompt 可以让模型把任意岗位的具体要求映射到这六个通用维度中。例如：

- 前端岗位的 TypeScript / Vue / React 进入“核心要求匹配”
- 产品岗位的需求分析 / 数据分析进入“核心要求匹配”
- 制造业岗位的设备操作 / 工艺流程 / 质量管理进入“核心要求匹配”
- AI Native / RAG / Agent 如果是 JD 明确硬性要求，进入“核心要求匹配”；如果只是“有更好”，进入“加分项匹配”；如果候选人缺少证据，则进入“风险与短板”

求职条件匹配规则：

- 城市只是求职条件的一部分，不再单独作为顶层评分卡
- 如果 JD base 在候选人意向城市中：城市条件匹配
- 如果不匹配：提示风险，但不强否决；原因是薪资、远程、机会质量可能改变候选人的城市选择
- 如果 JD 没有提到学历、语言、证书、到岗状态等条件，不要因为简历缺少这些信息而扣分
- 如果 JD 明确要求某个客观条件，而简历缺失或不满足，则写入 `gaps` 或 `requirementMatches`

## 未来后端 Prompt 结构建议

### 简历分析 Prompt

要求模型：

- 只基于输入简历内容判断
- 不要编造不存在的经历
- 每个技能信号必须给出证据
- 输出必须符合 `ResumeAnalysis` JSON schema

### JD 分析 Prompt

要求模型：

- 区分硬性要求和加分项
- 解析“熟练 / 精通 / 了解 / 优先”等语言强度
- 保留 JD 原文证据
- 输出必须符合 `JobRequirementAnalysis` JSON schema

### 匹配分析 Prompt

要求模型：

- 使用固定通用评分权重，不要创造新的顶层评分维度
- 具体岗位能力只能进入某个通用维度的 reason/evidence/gap，不能变成新的顶层字段
- 每个评分项必须有 reason
- 不要因为城市不匹配给出过强否定
- 输出必须符合 `JobAnalysis` JSON schema
- `matchScore` 应由 `scoreBreakdown` 加权计算或近似得到
